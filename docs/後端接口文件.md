## 1. 系統概念

### 1.1 角色

| 角色 | 是什麼 | 和後端的關係 |
|---|---|---|
| 凱比 | Nuwa 凱比機器人（Android 15），放在長者家，App 常駐畫面 | 呼叫第 4 節的 API。**沒有 Google Play 服務，不能用 FCM 推播**，一律由凱比輪詢 |
| 長者 | 吃藥的人。一台凱比綁定一位長者 | 資料都掛在長者底下 |
| 照服員 | 站點的照顧服務員，用後台網頁 | 管理長者、藥單、作息、綁定凱比；收 LINE 警示 |
| 家屬 | 長者的家人 | 收 LINE 警示（選用） |

### 1.2 核心原則

1. **後端是排程的唯一來源。** 凱比不能自己改提醒；凱比上的加藥、停藥、改作息都是送「變更申請」，後端收到就自動套用（不需要照服員核准），產生新的排程版本，凱比再拉回來。
2. **排程展開成「服藥事件」（occurrence）。** 一筆 occurrence ＝ 某一天某個時刻要吃的一包藥（同一時刻的藥合併成一包）。後端預先展開「昨天到 7 天後」，凱比斷網幾天也照樣提醒。
3. **凱比只回報事實**（提醒了、吃了、按了等一下）。後端依事件重算**正式狀態**（準時、晚吃、逾時、漏服），作為紀錄和發 LINE 的依據。
4. **規則是固定常數**（`Rules.kt`），凱比和後端用同一份數字，判定結果才會一致。不需要做「規則參數設定」功能。
5. **藥品一律對應目錄。** 藥單、凱比的申請都只引用 `catalogId`，不會有自由輸入的藥名。

### 1.3 名詞

| 名詞 | 意思 |
|---|---|
| 作息（routine） | 長者的早餐、午餐、晚餐、睡覺時間（`HH:mm`）。各時段的時刻由它推算 |
| 時段（slot） | 起床、早餐前、早餐後、午餐前、午餐後、晚餐前、晚餐後、睡前、指定時間（`CUSTOM`） |
| 處方項目（medication order） | 長者藥單上的一個藥：哪個目錄藥、劑量、時段、起訖日。ID 就是 API 裡的 `medicationId` |
| 排程版本（schedule version） | 每次發佈處方或作息的變更就 +1。凱比用版本號判斷要不要重新拉排程 |
| occurrence | 展開後的一包藥，ID 穩定（同一長者、同一天、同一時刻，跨版本不變） |
| T | occurrence 的 `scheduledAt`（該吃的時刻） |
| 晚吃期限（lateDeadline） | 超過這個時間就不能補吃，算漏服。由後端算好放在 occurrence 裡 |
| 變更申請（change request） | 凱比送出的加藥、停藥、改作息、清空藥單、目錄沒有的藥 |
| outbox | 凱比本機的待送佇列。斷網時事件和申請留在這裡，連上後補送 |

### 1.4 資料流

```
照服員（後台）                     後端                                    凱比
─────────────────────────────────────────────────────────────────────────────────────
建長者、設作息、開藥單 ──▶  medication_orders、elders
按「發佈」             ──▶  展開 occurrence、版本 +1
                                                         ◀── A5 心跳（前景每 1 分、背景每 15 分）
                            回 latestScheduleVersion ──▶ 版本不同
                                                         ◀── B1 拉排程（If-None-Match）
                            回 occurrence（昨天～7 天後）──▶ 本機到點提醒（語音、畫面、通知）
                                                         ◀── C1 服藥事件（吃了、等一下、逾時…）
                            重算正式狀態
                            逾時、漏服、離線 ─▶ LINE 通知照服員、家屬
                                                         ◀── R2 變更申請（加藥、停藥、改作息）
                            自動套用、版本 +1 ──────────▶ 回新版本號，凱比立刻 B1
                                                         ◀── R1 藥袋照片（申請之後背景上傳）
```

## 2. 通用規格

### 2.1 基本

- Base URL：`https://<host>/api/v1/`，全程 HTTPS。凱比 App 的網址設定在 `app/build.gradle.kts` 的 `API_BASE_URL`。
- JSON、UTF-8。**欄位名稱 camelCase，和 `api/dto/` 的 Kotlin 欄位名稱完全相同。** 列舉的 JSON 值看 `@SerialName`，沒有 `@SerialName` 的就是列舉名稱本身（例如 `AFTER_BREAKFAST`）。
- 凱比會忽略不認識的欄位，所以後端可以多回欄位；但不能少回必填欄位。
- 選填欄位沒有值時，可以省略或給 `null`。

### 2.2 時間

- 時區固定 `Asia/Taipei`（+08:00，沒有日光節約）。「今天」「某一天」一律用台北時間算。
- 時刻：ISO 8601 含時區，到秒，例如 `2026-11-22T08:00:00+08:00`。
- 日期：`YYYY-MM-DD`。時段時間：`HH:mm`。
- **每個成功回應都要帶 `serverTime`**（有定義這個欄位的）。凱比用它算時鐘差，差超過 2 分鐘會警告。
- 服藥事件的 `occurredAt` 是凱比的時間，後端判定準不準時要用它（不是送到的時間）。

### 2.3 驗證

- 凱比用 `Authorization: Bearer <accessToken>`。只有 A1（登記）、A3（換 token）不需要。
- token 由 A1 發給凱比。格式由後端決定（不透明字串或 JWT 都可以），凱比不解析。
- access token 過期：回 401 `TOKEN_EXPIRED`，凱比會用 A3 換新；A3 也失敗就重新 A1 登記。
- 後台 API 用照服員帳號驗證，方式由後端決定。

### 2.4 Idempotency 與去重

- 凱比的這些 POST 都帶 `Idempotency-Key: <UUID>`：A1、A2、B2、C1、C3、R1、R2。
- 同一個 key 重送時，回傳第一次的結果（狀態碼和內容都一樣），不要重複處理。建議保留 24 小時。
- 另外還有業務上的去重，**一定要做**：
  - C1 服藥事件：以 `eventId` 去重。
  - R2 變更申請：以 `requestId` 去重，重送時回第一次的結果。
  - R1 照片：以 `sha256` 去重，重送回 200 和原本的 `uploadId`。
- 凱比的 outbox 會在網路不穩時重送，同一筆可能送好幾次。

### 2.5 快取（ETag）

- B1 排程、E1 目錄回應帶 `etag` 欄位（也建議放在 `ETag` header）。
- 凱比下次帶 `If-None-Match: <etag>`。內容沒變就回 **304**，不帶 body。
- **B1 的 ETag 要包含排程視窗的第一天**，例如 `"v7-2026-11-22"`。排程視窗每天往後滾，版本沒變但日期變了，也要回新的內容（第 6.8 節）。

### 2.6 錯誤格式

錯誤一律用 RFC 7807，`Content-Type: application/problem+json`：

```json
{ "type": "about:blank", "title": "Device not assigned", "status": 409,
  "code": "DEVICE_NOT_ASSIGNED", "detail": "這台凱比還沒有綁定長者。", "traceId": "tr_0002" }
```

- `code`：機器看的錯誤碼（下表）。
- `detail`：給人看的說明。**422 時凱比會把 `detail` 念給長者聽**，要寫成一般長輩聽得懂的中文短句。

| HTTP | `code` | 什麼時候 | 凱比怎麼處理 |
|---|---|---|---|
| 304 | — | ETag 沒變 | 不動 |
| 401 | `TOKEN_EXPIRED` | token 無效或過期 | A3 換 token 後重試一次；換不到就 A1 重新登記（本機排程保留，繼續提醒） |
| 403 | `DEVICE_DISABLED` | 這台凱比被後台停用 | 停止提醒、刪掉本機用藥資料，顯示「這台凱比已經停用了」 |
| 404 | `UNKNOWN_OCCURRENCE` | （C1 不回 404，放在 `rejected`） | 丟掉那筆事件 |
| 404 | `PAIRING_CODE_INVALID` | 後台綁定時配對碼錯或過期 | （後台用） |
| 409 | `DEVICE_NOT_ASSIGNED` | 還沒綁定長者，卻呼叫需要長者的 API | 清掉本機排程，回到配對畫面 |
| 413 | `PAYLOAD_TOO_LARGE` | 照片太大 | 不重試，照片留在凱比上，用 C3 回報 `upload.too_large` |
| 422 | `INVALID_ROUTINE`、`INVALID_REQUEST`、`UNKNOWN_CATALOG_ID`、`UNKNOWN_MEDICATION` | 申請內容不合理 | 把 `detail` 念給長者聽，不重試 |
| 429、5xx | — | 忙碌、故障 | 留在 outbox，之後重試 |

### 2.7 凱比的呼叫頻率（估容量用）

| API | 頻率（每台凱比） |
|---|---|
| A5 心跳 | App 在前景每 60 秒；背景每 15 分鐘；開機、網路恢復各一次。**一天約 1,000–1,440 次** |
| A4 查狀態 | 每次同步一次（同上）；還沒綁定時每 15 秒 |
| B1 排程 | 版本或日期變了才拉，平常大多是 304 |
| C1 事件 | 每包藥 1–5 筆（提醒、再提醒、等一下、吃了…），一天一二十筆 |
| E1 目錄 | 每天一次（大多 304） |
| R1、R2 | 長者操作時才有 |

## 3. 資料庫

以 PostgreSQL 為例，型別可依實際資料庫調整。ID 都用字串，格式由後端決定（範例用 `dev_`、`eld_`、`med_`、`upl_` 開頭），凱比不解析 ID。

### 3.1 關係

```
stations 1─n elders
elders 1─n devices（一台凱比只綁一位長者；一位長者可以有多台）
elders 1─n medication_orders n─1 medication_catalog
elders 1─n schedule_versions
elders 1─n dose_occurrences 1─n dose_events n─1 devices
devices 1─n device_tokens、pairing_codes、app_events
devices 1─n change_requests 1─n uploads
elders 1─n alerts、contacts
```

## 4. 凱比 API

除了標明的以外，都需要 `Authorization`。每支 API 開頭都要先檢查：

1. token 有效 → 否則 401 `TOKEN_EXPIRED`。
2. 凱比沒被停用 → 否則 403 `DEVICE_DISABLED`。
3. 需要長者的 API（B1、B2、C1、C2、R1、R2）：凱比已綁定 → 否則 409 `DEVICE_NOT_ASSIGNED`。

A2、A4、A5、C3、E1 在還沒綁定時也要能用。

| 編號 | 方法 | 路徑 | 用途 |
|---|---|---|---|
| A1 | POST | `/devices/register` | 登記，拿 token（不需要 Authorization） |
| A2 | POST | `/devices/me/pairing-code` | 取得配對碼 |
| A3 | POST | `/devices/token/refresh` | 換 access token（不需要 Authorization） |
| A4 | GET | `/devices/me` | 綁定狀態、長者、開花數 |
| A5 | POST | `/devices/me/heartbeat` | 心跳，順便問有沒有新排程 |
| B1 | GET | `/devices/me/schedule` | 取得排程 |
| B2 | POST | `/devices/me/schedule/ack` | 回報已套用的版本 |
| C1 | POST | `/devices/me/dose-events` | 批次上傳服藥事件 |
| C2 | GET | `/devices/me/adherence?date=` | 查某一天的正式狀態（凱比資料不見時還原用） |
| C3 | POST | `/devices/me/app-events` | 非服藥類的操作紀錄 |
| R1 | POST | `/devices/me/uploads` | 上傳藥袋照片 |
| R2 | POST | `/devices/me/change-requests` | 變更申請 |
| E1 | GET | `/medications/catalog` | 藥品目錄 |

### 4.1 A1 登記 `POST /devices/register`

- 什麼時候：App 第一次啟動；token 和 refresh token 都失效時。
- 不需要 Authorization。帶 `Idempotency-Key`。

Request（`RegisterRequest`）：

| 欄位 | 型別 | 必填 | 說明 |
|---|---|---|---|
| `hardwareId` | string | ✓ | Android ID |
| `serialNo` | string | | 目前 null |
| `model` | string | ✓ | 例如 `AIR-H300` |
| `osVersion` | string | ✓ | 例如 `15` |
| `appVersion` | string | ✓ | 例如 `0.2.0` |
| `appVersionCode` | int | ✓ | |

Response 201（`RegisterResponse`）：

| 欄位 | 型別 | 說明 |
|---|---|---|
| `deviceId` | string | |
| `accessToken`、`refreshToken` | string | |
| `expiresIn` | long | access token 幾秒後過期 |
| `assigned` | bool | 是否已綁定長者 |
| `serverTime` | string | |

後端：
- `hardwareId` 沒登記過：新增 `devices`，發 token。
- 已登記過：回**同一個** `deviceId`，作廢舊 token、發新的。綁定關係保留（安全考量見第 10 節第 1 點）。
- 範例：`A1-register.request.json`、`A1-register.response.json`。

### 4.2 A2 取得配對碼 `POST /devices/me/pairing-code`

- 什麼時候：凱比還沒綁定時，配對畫面顯示 6 位數字和 QR。凱比在碼到期前 1 分鐘自動換新。
- 帶 `Idempotency-Key`。沒綁定也能呼叫。

Response 201（`PairingCodeResponse`）：

| 欄位 | 型別 | 說明 |
|---|---|---|
| `code` | string | 6 位數字 |
| `expiresAt` | string | 10 分鐘後 |
| `qrText` | string | 凱比畫成 QR 給照服員用手機掃，例如 `https://<後台網址>/pair?code=482913` |
| `serverTime` | string | |

後端：
- 作廢這台凱比之前的碼，產生新碼（未過期的碼不能重複）。
- 照服員在後台輸入或掃這個碼、選長者，就完成綁定（第 5 節 `POST /devices/claim`）。
- 範例：`A2-pairing-code.response.json`。

### 4.3 A3 換 token `POST /devices/token/refresh`

- 不需要 Authorization，不帶 `Idempotency-Key`。
- Request：`{ "refreshToken": "…" }`。
- Response 200：`{ "accessToken": "…", "expiresIn": 2592000, "refreshToken": "…（選填，有給就換掉舊的）" }`。
- refresh token 無效：回 401 `TOKEN_EXPIRED`，凱比會重新 A1。
- 範例：`A3-token-refresh.*.json`。

### 4.4 A4 查狀態 `GET /devices/me`

- 什麼時候：每次同步一開始（開機、心跳時）；還沒綁定時每 15 秒。

Response 200（`DeviceMeResponse`）：

| 欄位 | 型別 | 說明 |
|---|---|---|
| `deviceId` | string | |
| `assigned` | bool | false 時凱比顯示配對畫面、不提醒 |
| `elder` | object NULL | `{ elderId, displayName, stationName }`。只放顯示需要的 |
| `timezone` | string | 固定 `Asia/Taipei` |
| `latestScheduleVersion` | int NULL | 長者目前的排程版本 |
| `rewards` | object NULL | 開花數 `{ flowers, todayComplete }`（第 6.7 節） |
| `serverTime` | string | |

- 停用時回 403。
- 範例：`A4-devices-me.response.json`。

### 4.5 A5 心跳 `POST /devices/me/heartbeat`

- 什麼時候：App 在前景每 60 秒；背景每 15 分鐘；開機、網路恢復各一次。
- 沒綁定也能呼叫。

Request（`HeartbeatRequest`）：

| 欄位 | 型別 | 說明 |
|---|---|---|
| `appliedScheduleVersion` | int NULL | 凱比目前套用的版本 |
| `deviceTime` | string | 凱比的時間 |
| `foreground` | bool | App 是否在畫面最上層。用來判斷「App 不在前景」警示 |
| `pendingEvents` | int | outbox 裡還沒送的筆數 |
| `diagnostics` | object | `{ appVersion, voice, exactAlarm, notificationPermission, batteryPct?, charging? }` |

Response 200（`HeartbeatResponse`）：

| 欄位 | 型別 | 說明 |
|---|---|---|
| `latestScheduleVersion` | int NULL | 和凱比的版本不同，凱比就去 B1 |
| `serverTime` | string | |
| `commands` | array | 保留欄位，凱比目前不處理，回 `[]` |

後端：
- 更新 `devices` 的 `last_heartbeat_at`、`foreground`、`pending_events`、`diagnostics`、`applied_schedule_version`、`clock_skew_sec`。
- `foreground=true` 時更新 `last_foreground_at`。
- 凱比恢復心跳時，結束這台的 `device_offline` 警示。
- 範例：`A5-heartbeat.*.json`。

### 4.6 B1 取得排程 `GET /devices/me/schedule`

- 什麼時候：開機；心跳、A4、C1、R2 回的版本和本機不同；日期變了。
- 帶 `If-None-Match`（上次的 `etag`）；ETag 一樣回 304。

Response 200（`ScheduleDto`）：

| 欄位 | 型別 | 說明 |
|---|---|---|
| `version` | int | 版本號 |
| `etag` | string | 例如 `"v7-2026-11-22"`（第 6.8 節） |
| `publishedAt`、`effectiveFrom` | string | 這個版本的發佈、生效時間 |
| `timezone` | string | `Asia/Taipei` |
| `changeSummary` | string NULL | 給凱比念的說明 |
| `changeSource` | string NULL | `initial`、`caregiver`、`device_request`。只有 `caregiver` 時凱比會跟長者說「照服員幫您更新了藥」 |
| `routine` | object | `{ breakfast, lunch, dinner, sleep }`，`HH:mm` |
| `medications` | array | 目前藥單（`MedicationDto`，下表）。**不含**已停的、已吃完（過了 `endDate`）的 |
| `occurrences` | array | 昨天到 7 天後的 occurrence（`OccurrenceDto`，下表），依 `scheduledAt` 排序 |
| `serverTime` | string | |

`MedicationDto`：

| 欄位 | 型別 | 說明 |
|---|---|---|
| `medicationId` | string | ＝ `order_id` |
| `catalogId` | string | |
| `displayName`、`genericName`、`brandName` | string | 從目錄來 |
| `dose` | object | `{ amount?, unit?, text }`。`text` 例如「1 顆」 |
| `route` | string | 預設 `oral` |
| `instructions` | string NULL | 例如「飯前」「飯後」（依時段推出） |
| `slots` | string[] | 實際的時段；需要時才吃是 `[]` |
| `customTimes` | string[] | `CUSTOM` 的時刻 |
| `weeklyOn` | string NULL | |
| `endDate` | string NULL | 吃到哪天（含）；null ＝ 一直吃 |
| `imageUrl` | string NULL | 目前不用 |

`OccurrenceDto`：

| 欄位 | 型別 | 說明 |
|---|---|---|
| `occurrenceId` | string | 穩定的 ID |
| `date` | string | |
| `slot`、`slotLabel` | string | 例如 `AFTER_BREAKFAST`、「早餐後」 |
| `scheduledAt` | string | T |
| `lateDeadline` | string | 晚吃期限 |
| `items` | array | `[{ medicationId, doseText, catalogId, displayName }]`。後兩個讓凱比在藥被停掉後還能顯示名稱，請一定要給 |

後端：
- 回傳視窗：今天 −1 天 到 今天 +7 天（台北時間），含頭尾。
- 內容的算法見第 6.2–6.4、6.8 節。
- 凱比以 `occurrenceId` 合併：已提醒、已吃的保留本機狀態；不見了的未來 occurrence 就取消提醒。**所以 ID 一定要穩定。**
- 範例：`B1-schedule.response.json`。

### 4.7 B2 回報已套用 `POST /devices/me/schedule/ack`

- Request：`{ "version": 13, "appliedAt": "…", "result": "applied" | "failed", "error": null }`。
- Response 200：`{ "serverTime": "…" }`。
- 後端：更新 `devices.applied_schedule_version`、`applied_at`。後台看得到每台凱比套用到哪一版。
- 範例：`B2-schedule-ack.request.json`。

### 4.8 C1 服藥事件 `POST /devices/me/dose-events`

- 什麼時候：事件發生就送；失敗的留在 outbox，有網路時補送。一批最多 100 筆。

Request：`{ "events": [DoseEventDto, …] }`

| 欄位 | 型別 | 說明 |
|---|---|---|
| `eventId` | uuid | 去重用 |
| `occurrenceId` | string | |
| `type` | string | 見 4.9 |
| `occurredAt` | string | 凱比時間 |
| `source` | string | `touch`（按畫面）、`voice`、`notification`（通知上的按鈕）、`system`（凱比依時間自己判定） |
| `detail` | object NULL | 例如 `snoozed` 帶 `{ "snoozeUntil": "…" }`；凱比自己判定的事件帶 `{ "foreground": "true" }` |

Response 200（`DoseEventResultDto`）：

| 欄位 | 型別 | 說明 |
|---|---|---|
| `accepted` | string[] | 收下的 `eventId` |
| `duplicates` | string[] | 收過的（重送），以及同一包的第二筆「吃了」 |
| `rejected` | array | `[{ eventId, code }]`，例如 occurrence 不存在或已被刪除 → `UNKNOWN_OCCURRENCE`。凱比會丟掉這些 |
| `scheduleVersion` | int | 長者目前的版本，和凱比不同時凱比會去 B1 |
| `serverTime` | string | |

後端：
- 每筆依序處理：
  1. `eventId` 收過 → `duplicates`。
  2. occurrence 不存在或已刪除 → `rejected`（`UNKNOWN_OCCURRENCE`）。
  3. 是 `taken`／`late_taken`，但這包已經有「吃了」→ 存下來但標 `ignored`，放 `duplicates`（以第一筆為準）。
  4. 其他 → 存下來，放 `accepted`。
- 收到事件後重算該 occurrence 的正式狀態（第 6.6 節）。**事件可能晚很多才送到**（凱比斷網），一律依 `occurredAt` 重算，已經發出的警示要能結束。
- 整批回 200，不要因為一筆不對就整批失敗。
- 範例：`C1-dose-events.*.json`。

### 4.9 服藥事件的種類

| `type` | 意思 | 誰產生 |
|---|---|---|
| `reminded` | 第一次提醒（畫面或通知已顯示、已說話） | system |
| `reminded_again` | 再提醒（T+15，或「等一下」到期） | system |
| `snoozed` | 按了「等一下」，`detail.snoozeUntil` | touch、notification |
| `taken` | 吃了（T−30 到 T+30 之間按，算準時） | touch、notification |
| `late_taken` | 逾時後、晚吃期限前才吃 | touch、notification |
| `overdue` | 凱比判定逾時（T+30） | system |
| `missed` | 凱比判定漏服（過了晚吃期限） | system |
| `declined_late` | 過了晚吃期限才按，凱比告訴長者這次不要補吃 | touch |
| `reminder_failed` | 提醒無法呈現（目前沒用到） | system |
| `not_reminded_device_off` | 凱比關機期間錯過，開機時已過晚吃期限 | system |

凱比判定的 `overdue`、`missed` 只是參考，後端要自己依規則算（第 6.6 節）。

### 4.10 C2 查某天狀態 `GET /devices/me/adherence?date=YYYY-MM-DD`

- 什麼時候：凱比本機沒有資料時（重灌、恢復啟用、重新綁定），會查昨天和今天，避免已經吃過的又提醒一次。

Response 200（`AdherenceDto`）：

```json
{ "date": "2026-11-22", "occurrences": [
  { "occurrenceId": "occ_20261122_AFTER_BREAKFAST_eld_0001", "status": "taken", "takenAt": "2026-11-22T08:03:12+08:00", "late": false } ] }
```

- `status`：正式狀態的小寫（`upcoming`、`due`、`taken`、`taken_late`、`overdue`、`missed`、`unknown_device_offline`）。凱比只看 `taken`、`taken_late`。
- 回這一天、目前有效的 occurrence。
- 範例：`C2-adherence.response.json`。

### 4.11 C3 操作紀錄 `POST /devices/me/app-events`

- Request：`{ "events": [{ eventId, type, occurredAt, detail? }] }`。
- Response 200：`{ "accepted": [eventId…], "serverTime": "…" }`。以 `eventId` 去重。
- 目前會送的 `type`：

| `type` | 意思 | `detail` |
|---|---|---|
| `device.boot` | 凱比開機 | |
| `app.updated` | App 更新完成 | |
| `device.time_changed` | 凱比時間或時區被改 | |
| `notification.opened` | 長者點了提醒通知打開 App | `occurrenceId` |
| `app.exit` | 照服員在設定頁按「離開 App」 | |
| `upload.too_large` | 照片超過上限（413） | `bytes` |

- 範例：`C3-app-events.request.json`。

### 4.12 R1 上傳照片 `POST /devices/me/uploads`

- `multipart/form-data`。帶 `Idempotency-Key`。
- 欄位：`file`（JPEG 原圖，不縮圖）、`purpose`（`med_bag_photo`）、`requestId`（對應 R2 的申請）、`capturedAt`、`sha256`。
- Response 201：`{ "uploadId": "upl_0001", "sha256": "…" }`。同一個 `sha256` 再送：回 **200** 和原本的 `uploadId`。
- 單檔上限請至少 20 MB；超過回 413 `PAYLOAD_TOO_LARGE`。
- 凱比收到 2xx 就刪掉本機照片。
- 順序：凱比**先送 R2 申請、再背景上傳照片**。照片到的時候，對應的申請一定已經送過（申請被拒絕的，照片不會送）。
- 範例：`R1-upload.response.json`。

### 4.13 R2 變更申請 `POST /devices/me/change-requests`

- 什麼時候：長者在凱比上加藥、停藥、改作息、清空藥單，或拍了目錄裡沒有的藥。
- **收到就自動套用，不需要照服員核准。** 套用規則見第 6.5 節。

Request（`ChangeRequestDto`）：

| 欄位 | 型別 | 說明 |
|---|---|---|
| `requestId` | uuid | 去重用 |
| `type` | string | `add_medication`、`remove_medication`、`change_routine`、`clear_medications`、`unlisted_medication` |
| `createdAt` | string | 長者按下的時間 |
| `catalogId` | string | `add_medication` 必填 |
| `identifiedBy` | string | `add_medication`：`qr`、`ocr`、`user_selected` |
| `prescription` | object | `add_medication`：長者確認過的用法（下表） |
| `medicationId` | string | `remove_medication` 必填 |
| `reason` | string | `remove_medication`：`doctor_said_stop`、`added_by_mistake` |
| `routine` | object | `change_routine` 必填：`{ breakfast, lunch, dinner, sleep }` |

`prescription`（`PrescriptionDto`）。長者在凱比上一步一步回答：一天幾次 → 飯前飯後 → 每次幾顆 → 吃幾天 → 確認。

| 欄位 | 型別 | 說明 |
|---|---|---|
| `dosePerTime` | number | 每次幾顆，可以是 0.5。單位用目錄的 `defaultDose.unit` |
| `timesPerDay` | int | 1–4；**0 ＝ 需要時才吃** |
| `slots` | string[] | 藥袋 QR 寫的時段：`MORNING`、`NOON`、`EVENING`、`BEDTIME`。只在個數和 `timesPerDay` 一樣時才帶 |
| `mealRelation` | string | `BEFORE`、`AFTER`；一天 1 次時也可能是 `AT_BEDTIME`、`ON_WAKE`。沒帶用目錄的 |
| `durationDays` | int NULL | 吃幾天（1–365），從後端套用那天算起，含當天；null ＝ 一直吃 |
| `method` | string | `ORAL`、`TOPICAL`（藥袋 QR 有寫才帶） |

**凱比不會上傳辨識出來的藥名、QR 原文、OCR 全文**，只有上面這些結構化欄位。

Response 200（`ChangeRequestResultDto`）：

| 欄位 | 型別 | 說明 |
|---|---|---|
| `requestId` | string | |
| `status` | string | `applied`（已套用）、`no_change`（不用改）、`recorded`（只記錄） |
| `reason` | string NULL | `no_change` 的原因：`ALREADY_ACTIVE`、`NOT_ACTIVE`、`SAME_ROUTINE`、`ALREADY_EMPTY` |

- 內容不合理：回 **422**，`detail` 會念給長者聽（第 6.5 節有每種情況的文字）。
- 同一個 `requestId` 重送：回第一次的結果（包含 422）。

## 6. 計算規則

參考實作在 `api/.../reference/`，有單元測試。**凱比和後端要算出一樣的結果**，建議直接照參考實作翻寫，並拿它的測試案例驗證。

### 6.1 固定常數（`Rules.kt`）

| 常數 | 值 | 用途 |
|---|---|---|
| `EARLY_TAKE_MIN` | 30 | T−30 起按「吃了」算準時 |
| `REMIND_AGAIN_MIN` | 15 | T+15 再提醒（凱比端） |
| `OVERDUE_AFTER_MIN` | 30 | T+30 還沒吃 → 逾時 |
| `SNOOZE_MIN` | 10 | 「等一下」10 分鐘，最晚到 T+30（凱比端） |
| `LINE_NOTIFY_DELAY_MIN` | 2 | 判定逾時後再等 2 分鐘才發 LINE |
| `APP_NOT_FOREGROUND_ALERT_MIN` | 30 | App 連續 30 分鐘不在前景就通知 |
| `DEVICE_OFFLINE_AFTER_MIN` | 35 | 35 分鐘沒心跳算離線 |
| `SCHEDULE_DAYS_BEHIND`、`SCHEDULE_DAYS_AHEAD` | 1、7 | B1 視窗 |
| `MAX_EVENTS_PER_BATCH` | 100 | C1 一批上限 |
| `PAIRING_CODE_TTL_MIN` | 10 | 配對碼有效時間 |
| `UPLOAD_MAX_BYTES` | 20 MB | 照片上限（後端可以更大） |
| `MIN_MEAL_GAP_MIN`、`MIN_SLEEP_AFTER_DINNER_MIN` | 120、60 | 作息檢查 |
| `RANGE_BREAKFAST` 等 | 見程式 | 作息可調範圍 |

### 6.2 時段的時刻與 occurrence 展開（`OccurrenceExpander`）

時段的時刻由作息推算（`Slot.timeOf`）：

| 時段 | 時刻 |
|---|---|
| `WAKE` 起床 | 早餐 − 60 分 |
| `BEFORE_BREAKFAST` 早餐前 | 早餐 − 30 分 |
| `AFTER_BREAKFAST` 早餐後 | 早餐 |
| `BEFORE_LUNCH`、`AFTER_LUNCH` | 午餐 − 30 分、午餐 |
| `BEFORE_DINNER`、`AFTER_DINNER` | 晚餐 − 30 分、晚餐 |
| `BEDTIME` 睡前 | 睡覺 |
| `CUSTOM` 指定時間 | 處方的 `custom_times` |

展開某一天：
1. 找出這天有效的處方：沒停藥、`start_date ≤ 這天 ≤ end_date`（沒填就不限）、`weekly_on` 符合星期、不是 `as_needed`。
2. 每個處方的每個時段算出時刻（分鐘）。處方的 `slots` 空的就用目錄預設。
3. **同一個時刻的藥合併成一包**（一個 occurrence）。這包的 `slot` 取裡面最早的固定時段（都是 `CUSTOM` 才是 `CUSTOM`）。
4. `occurrenceId`：參考格式 `occ_<yyyyMMdd>_<slot>_<elderId>`，`CUSTOM` 時 slot 寫成 `CUSTOM<HHmm>`（例如 `occ_20261123_CUSTOM1745_eld_0001`）。格式可以自訂，但**同一長者、同一天、同一時刻一定要得到同一個 ID**。
5. `items`：這包裡每個藥的 `medicationId`、`doseText`、`catalogId`、`displayName`。

> 注意：兩個時段剛好同一時刻（例如作息改了之後早餐後＝午餐前）會合併成一包，ID 用較早的時段。

### 6.3 晚吃期限（`lateDeadline`）

- 這包裡**每一種藥**算一個期限，取最早的：
  - 一般的藥：到「下一次吃同一種藥」間隔的**一半**。例如一天兩次 08:00、18:30 → 08:00 那包期限是 13:15；18:30 那包的下一次是隔天 08:00，期限是隔天 01:15。
  - 一天一次的藥：下一次是 24 小時後，所以是 **12 小時後**（可以跨日）。
  - 每週一次的藥：當天 24:00。
- 不能早於 T+30。

### 6.4 發佈新版本時新舊合併（`PublishRules`）

發佈（後台按發佈、或凱比申請套用）時：

1. `effective_from`：後台選「立即」＝現在；「明天起」＝明天 00:00；凱比申請＝後端處理的時間。
2. 用新的處方和作息展開視窗內的 occurrence（fresh）。
3. 和目前有效的 occurrence（previous）合併：
   - **已經開始的**（`scheduledAt ≤ effective_from`）：維持原樣，不受新版本影響。
     - 例外：停藥、清空藥單時，還在進行中（還沒吃、還沒過晚吃期限）的那包要拿掉被停的藥；拿掉後沒有藥了就整包刪除。凱比會跟長者說「這個藥已經停了，不用吃」。
   - **還沒開始的**：照 fresh；fresh 沒有的就刪除（填 `removed_at`）。
   - **生效前的時段不產生新的 occurrence**。例如今天中午加的藥，今天早上的時段不會出現，也不算漏服。
   - **改作息時**：今天原本還沒開始、但新時間已經過了的時段，改成「現在」提醒（`scheduledAt = effective_from`，`lateDeadline` 至少再給 60 分鐘），避免今天那包被跳過。
4. 版本 +1，寫 `schedule_versions`，更新 `elders.schedule_version`。

### 6.5 變更申請怎麼套用（`ChangeRequestRules`）

共同：`effective_from` ＝ 後端處理的時間；套用後依 6.4 發佈新版本（`change_source = device_request`、`change_summary = null`）。

**`add_medication`（加藥）**

1. `catalogId` 不在目錄 → 422 `UNKNOWN_CATALOG_ID`「找不到這個藥。」
2. 檢查 `prescription`，不合理 → 422 `INVALID_REQUEST`：
   - `timesPerDay` 不在 0–4：「一天吃幾次要在 1 到 4 次之間。」
   - `dosePerTime ≤ 0`：「每次吃幾顆不對。」
   - `durationDays` 不在 1–365：「吃幾天要在 1 到 365 天之間。」
3. 長者已經有這個藥（同一個 `catalogId`，沒停、沒吃完）→ `no_change`，`reason = ALREADY_ACTIVE`。已經吃完（過了 `end_date`）的同一個藥不算，換成新的。
4. 新增處方：
   - `dose_text`：`dosePerTime` 有給就用「數字＋目錄單位」，否則目錄預設。寫法：0.5 →「半顆」、1 →「1 顆」、1.5 →「1 顆半」。
   - `slots`：見下表。
   - `end_date`：`durationDays` 有給 ＝ 今天 + `durationDays` − 1；沒給 ＝ null（一直吃）。
   - `weekly_on`：用目錄的。
   - `as_needed`：`timesPerDay = 0` 時為 true。
5. 回 `applied`、新版本、`medicationId`。

時段（`ChangeRequestRules.slotsFor`），「飯前飯後」＝ `prescription.mealRelation`，沒給就用目錄的 `mealRelation`：

| 情況 | 時段 |
|---|---|
| 沒有 `prescription`，或 `timesPerDay`、`slots` 都沒給 | 目錄預設 |
| `timesPerDay = 0` | 沒有（需要時才吃） |
| 有 `slots`（藥袋 QR） | 照 QR 的早、午、晚、睡前，再依飯前飯後對到餐前或餐後 |
| `timesPerDay = 1` | 選睡前 → 睡前；起床空腹 → 起床；飯前、飯後 → **目錄預設時段的那一餐**的餐前或餐後（目錄預設不是三餐時用早餐）；沒選 → 目錄預設的第一個時段 |
| `timesPerDay = 2` | 早、晚 |
| `timesPerDay = 3` | 早、午、晚 |
| `timesPerDay = 4` | 早、午、晚、睡前 |

早、午、晚對到餐前或餐後：飯前 → 早餐前、午餐前、晚餐前；起床空腹 → 「早」是起床，其他當飯後；其餘 → 早餐後、午餐後、晚餐後。睡前一律是睡前。

範例：目錄說飯後的降血脂藥（預設晚餐後），長者選「一天 1 次、飯前」→ 晚餐前；選「一天 2 次、飯後」→ 早餐後、晚餐後。

**`remove_medication`（停藥）**

- 沒有 `medicationId` → 422 `INVALID_REQUEST`「沒有指定要停哪一個藥。」
- 長者沒有這個處方（或已停）→ `no_change`，`NOT_ACTIVE`。
- 否則停藥（填 `removed_at`），未來的 occurrence 拿掉這個藥；進行中的照 6.4 的例外處理。

**`change_routine`（改作息）**

- 沒有 `routine` → 422 `INVALID_REQUEST`「沒有指定新的作息時間。」
- 檢查（`RoutineMinutes.validate`），不合理 → 422 `INVALID_ROUTINE`，`detail` 例如：
  - 「早餐時間要在 04:00 到 10:30 之間。」（午餐 10:00–14:30、晚餐 15:00–21:00、睡覺 18:00–23:45）
  - 「午餐要比早餐晚至少 2 小時。」「晚餐要比午餐晚至少 2 小時。」
  - 「睡覺時間要比晚餐晚至少 1 小時。」
- 和現在一樣 → `no_change`，`SAME_ROUTINE`。
- 否則改作息、發佈（6.4 的「改作息時」規則）。

**`clear_medications`（清空藥單）**

- 已經沒有藥 → `no_change`，`ALREADY_EMPTY`。
- 否則停掉全部的藥。已經過去的 occurrence（包含今天已吃的紀錄）不動。

**`unlisted_medication`（目錄裡沒有的藥）**

- 只記錄，不改排程，回 `recorded`。照片會接著從 R1 上傳，給照服員看要不要把這個藥加進目錄、幫長者開處方。

### 6.6 正式狀態（`DoseStatusRules.status`）

依事件和時間算，**用 `occurredAt`**：

1. 有 `taken` 或 `late_taken`：取最早的一筆。`occurredAt ≤ T+30` → `TAKEN`；否則 → `TAKEN_LATE`。
2. 有 `not_reminded_device_off` → `UNKNOWN_DEVICE_OFFLINE`。
3. 依現在時間：
   - 還沒到 T → `UPCOMING`
   - T 到 T+30 → `DUE`
   - T+30 到晚吃期限 → `OVERDUE`
   - 過了晚吃期限 → `MISSED`
4. 例外：結果是 `OVERDUE` 或 `MISSED`，但凱比離線、而且這包完全沒有事件 → `UNKNOWN_DEVICE_OFFLINE`。凱比可能只是斷網，吃了還沒傳上來，等事件補傳再算。

事件晚到時要重算；狀態從 `OVERDUE`／`MISSED` 變成 `TAKEN`／`TAKEN_LATE` 時，結束相關警示。

### 6.7 開花數（A4 的 `rewards`）

- `flowers`：今天以前，「當天所有 occurrence 都是 `TAKEN` 或 `TAKEN_LATE`」的天數（累計，沒有上限）。沒有 occurrence 的日子不算。
- `todayComplete`：今天是否已經全部吃完（今天要有 occurrence）。
- 只算有效的 occurrence（已刪除的不算）。

### 6.8 排程視窗與 ETag

- B1 回「今天 −1」到「今天 +7」的有效 occurrence。
- 視窗每天往後滾，所以每天 00:00 後要有「今天 +7」那天的 occurrence。兩種做法擇一：
  - (a) 每天 00:05 的背景工作，用目前的處方和作息展開新的那一天（**不改版本號**）。
  - (b) B1 時才展開：已經開始的用存下來的，還沒開始的用目前處方即時算（假後端是這樣做的）。
- ETag ＝ `"v<版本>-<視窗第一天>"`，例如 `"v7-2026-11-22"`。日期變了 ETag 就變，凱比會拿到新的一天。
- 已經過去的 occurrence 要永久保存（服藥紀錄）；凱比只拿視窗內的。

## 7. 背景工作與 LINE 通知

### 7.1 每分鐘

1. 找 `scheduled_at` 在最近 2 天內、還沒結束（不是 `TAKEN`、`TAKEN_LATE`、`MISSED`）的 occurrence，依第 6.6 節更新 `official_status`。
2. 警示（每種情況只發一次，記在 `alerts`）：

| 警示 | 條件（`DoseStatusRules`） | 結束 |
|---|---|---|
| `overdue` 逾時未服 | 狀態是 `OVERDUE`，而且現在 ≥ T+32（多等 2 分鐘，讓晚到的「吃了」趕上） | 收到吃了 |
| `missed` 漏服 | 狀態是 `MISSED` | 照服員處理 |
| `device_offline` 凱比離線 | 綁定中的凱比 35 分鐘沒有心跳 | 恢復心跳 |
| `app_not_foreground` App 不在前景 | 凱比在線，但最後一次 `foreground=true` 已經超過 30 分鐘 | 心跳回報 `foreground=true` |

- 凱比離線期間不判定逾時、漏服（狀態是 `UNKNOWN_DEVICE_OFFLINE`），只發「凱比離線」。
- 停用、未綁定的凱比不發警示。

### 7.2 LINE

- 發給這位長者的 `contacts`（依 `notify_types`）。
- LINE Notify 已在 2025 年 3 月停止服務，請用 **LINE Messaging API**（官方帳號推播）。聯絡人要先加官方帳號好友，才拿得到 `line_user_id`。
- 文字建議：
  - 逾時：「林阿公 早餐後 08:00 的藥還沒吃（已經過了 30 分鐘）。」
  - 漏服：「林阿公 早餐後 08:00 的藥沒有吃，已經過了可以補吃的時間。」
  - 離線：「林阿公的凱比已經 35 分鐘沒有連線，提醒可能還會照常響，但我們收不到紀錄。」
  - App 不在前景：「林阿公的凱比沒有顯示用藥提醒畫面已經 30 分鐘，請協助打開。」
- 發送失敗要重試，不要重複發（用 `alerts.notified_at` 控制）。

### 7.3 其他

- 每天：處理排程視窗（第 6.8 節做法 (a)）。
- 每小時：刪掉過期的配對碼、24 小時前的 idempotency key。
- 照片：依保存期限刪除（第 8 節）。

## 8. 安全與個資

- 凱比只能讀寫**自己綁定的長者**的資料；每支 API 都要用 token 對到的 `device_id` 查，不要相信路徑或 body 裡的 ID。
- token 只存雜湊；log 不要印 token、照片內容。
- `elders.display_name` 是凱比會顯示和念出來的稱呼，不要放全名以外的識別資料。
- **藥袋照片有長者姓名、病歷號、身分證等個資**：
  - 存在私有的物件儲存，只有有權限的照服員能看（短效的簽名網址）。
  - 保存期限、誰能看，請和營運單位訂好規則。
- 凱比上傳的申請不含辨識出來的藥名、QR 原文、OCR 全文；後端也不需要。
- 後台操作（綁定、停用、改藥、更正紀錄）要留稽核紀錄。

## 9. 串接與驗收

### 9.1 對照範例

- `api/src/test/resources/samples/` 每支 API 都有範例。後端的輸出用同樣的欄位、同樣的列舉值。
- `./gradlew :api:test` 會確認範例能被凱比的資料類別解析。後端可以把自己的輸出放進來跑。
- 計算規則對照 `api/src/test/kotlin/.../reference/` 的測試案例（展開、合併、申請、狀態），後端寫一樣的測試。

### 9.2 讓凱比 App 接上後端

1. `app/build.gradle.kts` 的 `API_BASE_URL` 填後端網址（例如 `https://api.example.com/api/v1/`）。空字串＝用 App 內建的假後端。
2. 建 debug 版、安裝到凱比（指令見 `README.md`）。
3. 在凱比上跑一輪：配對、後台改藥、斷網補送、401、停用、加藥、停藥、改作息、提醒、逾時、LINE。

### 9.3 假後端

`app/src/main/java/tw/kebbi/medreminder/sync/FakeBackend.kt` 是 App 內建的假後端，實作了全部 13 支凱比 API 和後台操作。行為有疑問時，可以看它怎麼做。它的限制：

- 資料存在凱比本機的一個 JSON 檔；token 不會過期；照片收下就丟。
- 沒有 LINE、沒有警示的背景工作。
- 只有一台凱比、一位測試長者。

## 10. 要和凱比端確認的事

1. **重新登記（A1）的安全性。**
   - 目前規則：同一個 `hardwareId` 再登記，回同一個 `deviceId`、保留綁定。好處是 App 重灌後不用重新配對。
   - 風險：`hardwareId`（Android ID）被冒用時，就能拿到長者的排程。
   - 建議：refresh token 給長一點（例如 1 年，每次使用就換新），讓重新登記只在重灌時發生；重新登記時發一則警示給照服員。要不要改成「重新登記一律要重新配對」，請和產品負責人確認。
2. **後台改藥（要發佈才生效）和凱比申請（立刻生效）會互相影響。**
   - 照服員改了藥還沒發佈時，凱比送出一筆申請，會把照服員還沒發佈的修改一起發佈出去。
   - 建議：處方分「草稿」和「已發佈」兩份；凱比的申請改已發佈的那份（也同步到草稿），後台發佈時把草稿覆蓋到已發佈。
3. **access token 有效期**：假後端是 30 天。後端可以自訂，凱比會自動換。
4. **照片保存期限、誰能看**：由營運單位決定。
5. **心跳 `commands`**：目前凱比不處理。以後要從後端叫凱比做事（例如立即同步），再一起定義。

有問題請在 GitHub 開 issue，標題寫 API 編號（例如「B1 occurrenceId 的格式」）。
